My Health Log

Flutter 기반 개인 건강 기록 앱을 직접 기획하고 구현한 뒤, 요구사항 기반 QA부터 Regression, Android Release까지 검증한 개인 QA 프로젝트입니다.

Problem

체중, 혈압, 수분, 운동, 수면, 컨디션, 복약, 검사 결과를 날짜 기준으로 기록하고 비교하기 어렵다는 문제를 V1 범위로 정의했습니다.

App Structure

Home오늘 건강 요약, 오늘 복약 상태
Health체중, 혈압, 수분, 운동, 수면, 컨디션 CRUD
Medication약 등록/수정, 복용 시간, Soft Delete, 복약 Toggle
Lab검사 결과 CRUD, 날짜별 Group / Detail
Statistics체중, 혈압, 검사 수치 변화와 실제 기록값

Main Features

  • HealthRecord는 날짜별 1개 Record 정책과 Local Persistence를 검증했습니다.
  • Medication 삭제 후 과거 MedicationLog 보존을 위해 Soft Delete로 처리했습니다.
  • MedicationLog는 날짜와 timeSlot 기준으로 복용 완료와 취소 상태를 분리했습니다.
  • LabResult는 날짜별 그룹과 상세 화면, 동일 date + testName 중복 방지를 검증했습니다.
  • Statistics는 별도 통계 테이블 없이 저장된 HealthRecord / LabResult를 조회해 표시했습니다.

Data Model

HealthRecord날짜별 건강 수치와 상태 기록
Medication복용약, 복용 시간, 활성 상태
MedicationLogMedication 1:N 관계의 날짜별 복용 여부
LabResult검사 날짜, 항목, 결과값, 단위

QA 관점에서는 어떤 데이터가 어떤 화면과 상태에 영향을 주는지 기준을 세우고 CRUD와 데이터 일관성을 검증하는 데 초점을 맞췄습니다.

What I Learned

  • 요구사항과 실제 구현 결과의 일치 여부를 끝까지 확인하는 것이 QA에서 중요하다는 점을 확인했습니다.
  • 화면 표시뿐 아니라 DB 상태와 데이터 관계를 함께 검증해야 CRUD 안정성을 명확히 볼 수 있었습니다.
  • 기능 추가 시 기존 데이터 Migration과 Regression 범위를 함께 고려해야 함을 경험했습니다.
  • Release 이후에도 다른 관점의 Visual QA에서 결함이 발견될 수 있음을 확인했습니다.
  • 기획부터 Release까지 직접 진행하며 기능 간 영향 관계를 더 구체적으로 이해했습니다.
